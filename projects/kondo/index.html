Kondo — NFQ

The data pipeline behind Allfunds' Kondo platform: revenue data moving from GCP into AWS across a PostgreSQL environment with 1,000+ tables — plus AI proof-of-concepts built alongside it.

Problem

Kondo processes revenue information for Allfunds at real financial-platform scale — a PostgreSQL environment with 1,000+ tables and thousands of records arriving daily. That data originated on Google Cloud Platform but needed to land, transformed and reconciled, in AWS, feeding the revenue calculations and reporting that both internal teams and end-user applications depend on. At that volume, the pipeline's correctness and its cost both matter: a slow or wasteful transform step gets expensive fast when it runs against thousands of tables every day.

Technical decisions

I built a significant part of the GCP-to-AWS pipeline using Python, PySpark and SQL to transform, process and load the data, and designed the SQL queries and database tables that support the underlying revenue calculations and the reporting built on top of them. Processing workflows ran on AWS S3, Lambda and Step Functions — Step Functions in particular made it possible to orchestrate multi-stage transforms with clear retry and error-handling behaviour rather than chaining Lambdas together informally.

The most consequential piece of work was redesigning parts of the data flow specifically to cut unnecessary processing — re-scoping which tables and records actually needed to move through each transform stage rather than reprocessing everything by default. That's a data-engineering problem as much as a cost one: at 1,000+ tables, avoiding redundant work compounds daily. All of this moved through development, pre-production and production environments via GitLab, the standard path any change took before it touched real revenue data.

Result

The redesigned data flow reduced unnecessary data processing and computational workload, directly lowering cloud computing costs while keeping the same revenue-reporting output correct downstream. The pipeline became one of the concrete pieces of infrastructure turning raw financial data into the structured information Allfunds' client reporting and end-user applications rely on.

Also on this team: AI proof-of-concepts

Alongside the data platform work, I contributed to NFQ's AI department, building proof-of-concepts for automated receipt recognition, payment-status detection and duplicate-document detection — turning scanned invoices and receipts into structured, queryable data (OCR extraction, field parsing, and a duplicate-document detector comparing extracted fields rather than relying on exact file matches). These were used directly in client-facing demonstrations for prospective clients.

Next steps

The natural next layer for the data platform at this scale is closer observability on the transform stages themselves — per-table cost and latency tracking, so the next redundant-processing opportunity shows up in a dashboard rather than needing to be found by hand.
